## 4. Модель данных и функции

Задача - плоский объект из четырёх полей: `id` (положительное безопасное целое), `title` (строка, после `trim()` от 1 до 100 символов), `completed` (только `true`/`false`, при создании всегда `false`), `priority` (строго `"low"`, `"medium"` или `"high"`, по умолчанию `"medium"`).

Ответственность разнесена по файлам:

| Файл | За что отвечает |
|---|---|
| `src/data.js` | только данные: общий набор `demoTasks` и набор варианта `variantTasks` |
| `src/task-service.js` | девять функций: проверки полей и операции над переданным массивом, без вывода |
| `src/task-extra.js` | расширение `getPrioritySummary` |
| `src/main.js` | сценарии, вывод и обработка отказов |
| `checks.js` | сравнение фактических результатов с ожиданиями |

Форматы результатов: создание возвращает `{ ok: true, task }`, изменяющие операции - `{ ok: true, tasks }`, отказ везде `{ ok: false, error: "текст" }`. Чтение проще: `findTaskById` отдаёт объект или `undefined`, `getPendingTasks` и `getTaskTitles` - новые массивы, `getTaskStats` - объект сводки.

Чтобы не дублировать код, внутри модуля лежат три непубличные функции: `checkId`, `normalizeTitle` и `checkPriority`. Наружу они не экспортируются.

**Почему id не равен индексу:** индекс - это текущее место в массиве, он сдвигается после удаления соседа. `id` закреплён за записью навсегда. После удаления `id = 7` в общем наборе остаются `[1, 4, 10]`, и задача с `id = 10` стоит на индексе 2 - обращение `tasks[10]` дало бы `undefined`.

**Почему getTaskStats возвращает число, а не строку с процентом:** `toFixed()` возвращает строку, а с числом ещё можно считать дальше и сравнивать. Округление - дело вывода, поэтому `progress.toFixed(1)` вызывается в `main.js`. В проверке 18 видно, что для трёх задач с одной выполненной прогресс равен `33.33333333333333`, а на экран идёт `33.3%`.

**Какие объекты копируются при изменении задачи:** новый массив обязателен всегда, новый объект - только у изменяемой записи (`map` + spread). Остальные записи переиспользуются как есть, копировать их незачем. В проверке 37 это видно прямо: `updated[1] === tasks[1]`, но `updated[0] !== tasks[0]`.

## 8. Расширение

Выполнен **вариант Б - сводка по приоритетам**, модуль [`src/task-extra.js`](./src/task-extra.js).

**Контракт:** `getPrioritySummary(tasks)` принимает корректный массив задач и возвращает объект `{ low: { total, pending }, medium: { ... }, high: { ... } }`. Все три приоритета присутствуют всегда, даже если задач с таким приоритетом нет. `pending` считает записи с `completed === false`. Входной массив и его объекты не меняются - функция только читает. Реализовано циклом `for...of` по заранее собранному объекту-накопителю.

| Проверка | Входные данные | Ожидаемый результат | Фактический результат | Итог |
|---|---|---|---|---|
| Смешанный набор | `demoTasks` | low 1/1, medium 2/0, high 1/1 | совпало | Пройдено |
| Пустой список | `[]` | все три приоритета по 0/0 | совпало | Пройдено |
| Один приоритет | две задачи `high`, одна выполнена | low 0/0, medium 0/0, high 2/1 | совпало | Пройдено |
| Неизменность входных данных | `demoTasks` до и после вызова | массив совпадает с исходным | совпало | Пройдено |

В `main.js` сводка выводится и по общему набору, и по итоговому набору варианта: там получается low 3/3, medium 2/1, high 1/0.

## 9. Вывод

По сравнению с ПР1 поменялось главное: в первой работе всё жило в отдельных переменных и печаталось прямо на месте расчёта, тут данные - массив объектов, а расчёты возвращают значения и ничего не выводят. Из-за этого один и тот же `getTaskStats` спокойно работает и в сценарии, и в проверках, а в ПР3 его же можно будет вызвать из обработчика события - менять придётся только вывод.

Неизменность проверял в двух местах: печатал исходный массив после всех операций и отдельно сравнивал ссылки - новый массив обязателен, новый объект нужен только у изменённой записи. Проверка 33 с `Object.freeze` оказалась самой полезной: если бы где-то осталось присваивание свойству входного объекта, она бы сразу упала.

Исправлять пришлось два раза, и оба - в своих проверках, а не в модуле: неверно посчитанное ожидание в проверке 37 и сравнение дробного прогресса на точное равенство в проверке 39. Второе поучительнее - `2/6*100` и `100/3` в double не совпадают, так что проценты сравнивать с допуском.

Основной вывод: если данные не мутировать, отлаживать сильно проще - старое состояние всегда под рукой.
