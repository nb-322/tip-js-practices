## Запуск

Рабочая папка: `practice-05` внутри личного репозитория.

```bash
npm run check:api
npm test
```

`npm test` выполняет четыре набора подряд: проверки готового API, модульные проверки клиента, интеграционные и собственные. Для ручного сценария нужны два терминала.

Терминал 1:

```bash
npm start
```

Терминал 2:

```bash
npm run example:order
npm run example:fetch
npm run client
```

Адрес API по умолчанию `http://127.0.0.1:5505/api`, переопределяется переменной `API_URL`. Порт не менялся.

## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Ждал, что синхронный код пройдёт целиком, потом микрозадачи в порядке постановки, потом таймер |
| Фактический результат | A, B, C, D, E, F | Прогноз совпал, но по неочевидной причине: `D` оказался раньше `E` не потому, что `then` «важнее», а потому что продолжение после `await` встало в очередь микрозадач позже, чем обработчик `then` |

Синхронно выполняются `A`, `B` и `C`: вызов `demonstrateAwait()` не ждёт, он доходит до `await` и возвращает управление, поэтому `C` печатается до всего асинхронного. В очередь микрозадач попадают `D` (обработчик `Promise.resolve().then`) и `E` (продолжение после `await null`), и выполняются они в порядке постановки. Таймер `F` с задержкой `0` выполняется последним, потому что это макрозадача: цикл событий берёт её только после того, как очередь микрозадач опустеет, а `0` означает «не раньше чем через 0 мс», а не «немедленно».

Если удалить обработчик `Promise.resolve().then(...)`, метка `D` просто исчезнет, а относительный порядок остальных не изменится: `E` по-прежнему будет микрозадачей перед таймером.

По пункту 6 задания добавил собственный обработчик `Promise.resolve().then(() => log("G: ..."))` после вызова `demonstrateAwait()`. Прогноз: `G` встанет между `E` и `F`, потому что он поставлен в очередь микрозадач третьим, уже после `D`, а продолжение после `await` попадает туда раньше него. Фактический вывод совпал:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: собственный обработчик Promise
F: задача таймера
```

Отдельно проверил шесть адресов через `fetch` в скрипте:

| Запрос | Статус | `response.ok` | `Content-Type` | Форма тела |
|---|---:|---|---|---|
| `/api/health` | 200 | `true` | `application/json; charset=utf-8` | `{ data: { status: "ok" } }` |
| `/api/tasks` | 200 | `true` | `application/json; charset=utf-8` | `{ data: массив из 12, meta }` |
| `/api/tasks?completed=false&priority=high` | 200 | `true` | `application/json; charset=utf-8` | `{ data: массив из 3, meta }` |
| `/api/tasks/25` | 200 | `true` | `application/json; charset=utf-8` | `{ data: объект задачи }` |
| `/api/tasks/999` | 404 | `false` | `application/json; charset=utf-8` | `{ error: { code: "TASK_NOT_FOUND", message, details } }` |
| `/api/categories` | 200 | `true` | `application/json; charset=utf-8` | `{ data: массив из 3, meta }` |

Главное наблюдение: при `404` обещание `fetch` не отклоняется. Тело приходит нормальным JSON, меняется только `response.ok` и статус, поэтому ошибку надо искать самому, а не ловить через `catch`.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API, не изменялся |
| `src/api-client.js` | `ApiError`, `buildUrl` и общий JSON-клиент: транспорт, статусы, тайм-аут, отмена |
| `src/task-api.js` | Предметный слой задач: допустимые фильтры, три запроса, проверка схемы ответа |
| `src/task-api-extra.js` | Расширение: частичная загрузка через `Promise.allSettled` |
| `src/variant.js` | Номер варианта и его фильтры, без логики |
| `src/main.js` | Консольный сценарий: сбор клиента, вывод таблицы, разбор ошибки |

`fetchFn` передаётся в `createApiClient` аргументом, чтобы модуль можно было проверить без сети: в `check:client` все 26 сценариев работают на подменённой функции, которая возвращает заранее собранный `Response` или бросает нужную ошибку. Если бы клиент звал глобальный `fetch` сам, пришлось бы либо поднимать сервер ради каждой проверки, либо патчить глобальный объект.

HTTP-ошибки проверяются отдельно от сетевых, потому что это разные события. `404` означает, что сервер жив и ответил по контракту, просто записи нет; `network` означает, что ответа не было вообще. Пользователю в первом случае показывают «задача не найдена», во втором - «нет связи», и повторять запрос имеет смысл только во втором.

JSON после разбора всё равно проверяется по контракту, потому что успешный `JSON.parse` говорит только о синтаксисе строки. Ответ может быть валидным JSON и при этом не соответствовать модели: задача без `categoryId`, `completed` строкой, повторяющиеся id, `meta.total` не совпадающий с длиной `data`. Такие случаи превращаются в `ApiError` с видом `invalid-response` в `task-api.js`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `parseBaseUrl` через `new URL`: требует схему `http`/`https`, запрещает query и hash; путь приводится к виду с завершающим `/`, ведущий `/` у `path` срезается | 01, 04 |
| Кодирование query-параметров | `URLSearchParams` через `url.searchParams.set`; `undefined`, `null` и `""` пропускаются, `false` и `0` приводятся к строке | 02, 03 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }` в каждом запросе | 05 |
| Проверка `response.ok` | Выполняется до любого разбора тела; поля берутся из `payload.error`, если тело оказалось JSON | 08, 09, 16 |
| Проверка `Content-Type` | Регулярное выражение `application/...json` на успешном ответе, до `response.json()` | 10 |
| Разбор JSON | `await response.json()` в отдельном `try`, ошибка превращается в `invalid-response` с исходным `SyntaxError` в `cause` | 11 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` на каждый запрос, значение можно переопределить в вызове | 14 |
| Внешняя отмена | `AbortSignal.any([externalSignal, timeoutSignal])`; вид ошибки определяется по тому, какой из двух сигналов сработал, а не по тексту исключения | 15 |

Отдельное решение: `fetch` оборачивается в собственный `try`, и только его отказ классифицируется как `network`. Если положить в тот же `try` разбор ответа, то `ApiError` с видом `http`, созданная вручную, была бы поймана тем же `catch` и переписана в `network`. Проверка 16 ловит именно это.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]`, `meta.total` 12 |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `[{ id: 1, name: "Учёба" }, { id: 2, name: "Проект" }, { id: 3, name: "Организация" }]` |
| `loadInitialData({ priority: "high" })` | `{ tasks: 5 задач, categories: 3 категории, meta: { total: 5, filters } }` |

Правила проверки: у задачи обязательны положительный безопасный целый `id`, непустая строка `title` до 100 символов после `trim`, логический `completed`, приоритет из трёх значений и положительный целый `categoryId`; у категории - `id` и непустое `name`. Дополнительно коллекция отклоняется, если `data` не массив, если id повторяются или если `meta.total` не равен длине `data`. Любое несовпадение превращается в `ApiError` с видом `invalid-response`, а не исправляется на месте.

Фильтры проверяются до запроса и только четыре: `completed`, `priority`, `categoryId`, `q`. Логическое `false` остаётся логическим внутри предметного кода, в строку его превращает уже `URLSearchParams`, поэтому фильтр «невыполненные» не теряется.

## Последовательная и параллельная загрузка

Сравнение на двух запросах `/api/debug/delay?ms=150`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 330 | 312 | 321 | Около суммы задержек: второй запрос стартует только после ответа на первый |
| `Promise.all` | 159 | 157 | 155 | Около одной задержки: оба запроса уже отправлены, ожидание общее |

Причина разницы не в скорости кода, а в моменте старта: при двух подряд идущих `await` второй `fetch` вызывается только после того, как первый завершился, а при `Promise.all` обе функции вызваны до общего ожидания, и задержки сервера накладываются друг на друга. `Promise.all` при этом ничего не запускает сам, он лишь ждёт уже созданные промисы, поэтому важно именно начать оба запроса до `await`. Числа зависят от машины и сети, повторять их как универсальное ускорение нельзя: выигрыш появляется только там, где запросы независимы.

## Отладка

Точки останова ставились в `requestJson`: на строке `response = await fetchFn(...)` (до запроса), сразу после неё, на проверке `if (!response.ok)` и перед `return await response.json()`, плюс в `catch`, где вызывается `classifyFailure`.

Успешный запрос `getTaskById(25)`: до `fetch` в Scope видно `url` `http://127.0.0.1:5505/api/tasks/25`, `options.method` `GET`, заголовок `Accept: application/json` и `signal` с `aborted: false`. После получения ответа `response.status` 200, `response.ok` `true`, `Content-Type` `application/json; charset=utf-8`. Разобранный payload - `{ data: { id: 25, ... } }`, и уже `task-api.js` достаёт из него `data` и проверяет по модели.

Ошибочный запрос `getTaskById(999)`: URL `http://127.0.0.1:5505/api/tasks/999`, `response.status` 404, `response.ok` `false`, тело при этом корректный JSON. Ветка `!response.ok` читает `payload.error`, и собирается `ApiError` с `kind: "http"`, `status: 404`, `code: "TASK_NOT_FOUND"`, `details: { id: 999 }`. В `catch` вокруг `fetch` управление не попадает вовсе - это видно по тому, что точка останова в `classifyFailure` не срабатывает, пока API запущен.

## Дополнительное задание

Выполнено **расширение А - частичный результат через `Promise.allSettled`**, модуль [`src/task-api-extra.js`](./src/task-api-extra.js).

Контракт: `createPartialLoader(api)` принимает объект, созданный `createTaskApi`, и возвращает `loadInitialDataSettled(filters)`. Результат всегда один и тот же по форме:

```js
{
  ok: boolean,
  tasks: task[] | null,
  meta: object | null,
  categories: category[] | null,
  errors: {
    tasks: { kind, status, code, message } | null,
    categories: { kind, status, code, message } | null
  }
}
```

Функция никогда не отклоняется: оба запроса идут через `Promise.allSettled`, и отказ одного не отменяет результат другого. Причина отказа приводится к простому описанию с видом, статусом и кодом, чтобы вызывающий код не разбирал исключение сам. Обязательный `loadInitialData` не тронут и по-прежнему отклоняется целиком при любой ошибке.

| № | Сценарий | Ожидаемый результат | Фактический результат | Итог |
|---:|---|---|---|---|
| 7 | Оба запроса успешны, фильтр варианта | `ok: true`, пять задач, три категории, ошибок нет | id `[4, 13, 16, 25, 34]`, 3 категории, `errors` пустые | Пройдено |
| 8 | Отказ задач (`network`), категории доступны | `ok: false`, `tasks: null`, категории на месте | Категории получены, `errors.tasks.kind` `network`, `errors.categories` `null` | Пройдено |
| 9 | Отказ категорий (`http` 503), задачи доступны | `ok: false`, задачи на месте, описан статус и код | id `[4]`, `errors.categories.status` 503, код `SERVICE_UNAVAILABLE` | Пройдено |
| 10 | Отказ обоих запросов | `ok: false`, обе причины описаны отдельно | `tasks` и `categories` `null`, оба `errors` с видом `timeout` | Пройдено |

## Вывод

ПР5 отделила транспорт от предметной логики. `api-client.js` ничего не знает про задачи: он умеет собрать URL, сходить за JSON, уложиться во время и правильно назвать причину отказа. `task-api.js` ничего не знает про `fetch`: он проверяет фильтры до запроса и форму данных после. Благодаря этому все 26 модульных проверок работают без сети, а те же модули в интеграционном наборе отвечают на настоящие ответы сервера.

Шесть видов ожидания и отказа различаются так. Ожидание Promise - это просто «результата ещё нет», само по себе не ошибка. HTTP-ошибка значит, что сервер жив и ответил по контракту, но запрос неверен или записи нет, и обещание `fetch` при этом не отклоняется. Сетевая ошибка значит, что ответа не было вообще. `invalid-response` - ответ пришёл, но им нельзя пользоваться: не тот `Content-Type`, битый JSON или данные не по модели. `timeout` - мы сами перестали ждать по истечении лимита. `aborted` - ждать перестал вызывающий код. Для пользователя это разные сообщения, а для программы - разное решение о повторе: повторять осмысленно `network`, `timeout` и `503`, но бессмысленно `404` и `invalid-response`.

Ошибок в реализации не было, все четыре набора прошли с первого запуска. Дважды ошибался в собственных проверках: сначала ждал в категории 3 две невыполненные задачи вместо одной, потом ждал в `meta.filters` пустую строку там, где сервер отдаёт `null`. Оба раза неверным было моё ожидание, а не код - и это хорошая иллюстрация к тому, зачем ответ сервера вообще проверяется по контракту, а не принимается на веру.
